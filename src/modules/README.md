# V2 modules

Notification & System Logs implements Admin-only in-system and email sending through `POST /api/v1/notifications` and `POST /api/v1/notifications/email`. All active roles can read and update their own supported delivery channels through `GET/PATCH /api/v1/notifications/preferences`; preferences default to both channels enabled and updates are audited. Inbox listing, read state and notification history remain separate use cases.

Admin-only `POST /api/v1/notifications/email` sends text-only email through the configured SMTP transport to up to 20 explicitly selected active users. It snapshots recipient email addresses, records `PENDING` delivery rows before network I/O, then marks each attempt `SENT` or `FAILED` without exposing provider errors. Partial delivery is returned with sent/failed counts. Retry, templates, attachments, HTML email and bulk role audiences are outside this use case.

Control Evidence references: `GET`/`POST /compliance/controls/:controlId/evidence` and `POST /compliance/controls/:controlId/evidence-links` are active, using the existing `evidence_items` and `control_evidence_links` tables. Only active Security Officers and assigned Employee Control Owners can act. Linked records stay visible across statuses; candidates are ownership-scoped, Active, already collected and within validity, excluding existing pairs, paginated at maximum 10. Add atomically creates metadata/reference + link + audit; Link reuses an accessible record and records relevance. Neither marks Evidence reviewed, uploads/verifies files, changes assessment history nor recalculates Risk. New references require stable credential-free HTTPS URLs; external document authorization remains external. Add supports identical requestId replay and rejects conflicting reuse/duplicate accessible document+collection time. Link is additive/idempotent. Evidence expiry is checked at new assessment time; previously saved assessment history is not deleted or retroactively recomputed. The current schema links Evidence to the Control, not a per-assessment immutable file snapshot, so this feature must not be described as versioned evidence custody. File upload, review, edit, unlink, archive and explicit Control-to-Risk linking remain separate use cases. No schema change or migration is included.

Control catalog preparation for Risk Assessment is implemented through `POST /compliance/controls`, `GET`/`PATCH /compliance/controls/:controlId` and `GET /compliance/controls/owner-options` under the API prefix. These extend the existing shared `security_controls` resource and `/compliance` route contract; the physical compatibility module is not a claim that Assess Control Effectiveness belongs to Policy Management. Catalog Create/Edit is Security Officer-only. Contextual Employee Control Owners gain `compliance.assess-controls` navigation only while assigned at least one control; assessment APIs retain resource ownership checks. Codes are immutable, new owners are active Employees or Security Officers, and edits require a reason and exact revision. Applicability/implementation are locked after the first assessment to prevent historical effectiveness from being silently reinterpreted. Evidence, assessments and Asset/Risk/Incident links are not changed by catalog writes. No new database tables or migrations are needed. Evidence upload and explicit Control-to-Risk link management remain separate use cases.

Business Service Deactivate: Security Officer `GET /api/v1/business-services/:serviceId/deactivation-check` shows usage; `POST /:serviceId/deactivate` requires expectedUpdatedAt, confirmationName and reason. Only unused Active services may transition to Inactive: Active assets and directly scoped Open/Under treatment/Accepted Risks block; Archived assets and Closed/Archived Risks remain linked for history. Actor/status/version/usage checks plus audit are atomic in a Serializable transaction; concurrent changes return 409. No deletion, reactivation, relinking, Risk synchronization or schema changes. The reason, actor and timestamp live in existing audit_logs (BUSINESS_SERVICE_DEACTIVATED), not new Business Service columns.

Business Service Edit: `PATCH /api/v1/business-services/:serviceId` permits active Security Officers to edit name, description and owner only on Active services. Requires expectedUpdatedAt; rejects stale writes, duplicate names and new inactive owners. Retains unchanged inactive owners, supports explicit unassignment, and records before/after metadata atomically in audit. Status, identity, Asset membership and Risk scope are not editable here.

Business Service creation: `POST /api/v1/business-services` and `GET /api/v1/business-services/owner-options` require an active Security Officer. Creates Active service only, optional active owner, normalized nonduplicate name; atomic audit, no asset links or Risk synchronization, no schema changes. See OpenAPI for validation limits. Name concurrency guard covers this API path, not direct database inserts.

IT Asset Management also exposes read-only `GET /api/v1/business-services`, `GET /api/v1/business-services/:serviceId`, and `GET /api/v1/business-services/:serviceId/assets` for active Security Officers. List/search and linked assets are bounded and paginated; inactive services and archived assets remain visible for review. These read endpoints do not modify any record, relink assets or synchronize existing Risk scopes. See the corresponding OpenAPI contracts.

The active backend uses the 56-table baseline in `project-docs/new/database.sql` plus applied additive migrations (64 tables currently). The domain folders follow the current Project Tracking document. Refer to the implemented route list in this file rather than assuming unlisted use cases are active.

Implemented routes are `/api/v1/health/live`, `/api/v1/health/ready`, `/api/v1/auth/login`, `/api/v1/auth/refresh`, `/api/v1/auth/logout`, protected `/api/v1/users/me`, `GET /api/v1/risks`, `GET /api/v1/risks/:riskId`, `POST /api/v1/compliance/policies`, `GET /api/v1/compliance/policies/drafts/mine`, `PATCH /api/v1/compliance/policies/:policyId/drafts/:versionId`, `POST /api/v1/compliance/policies/:policyId/versions/:versionId/submit`, Admin submitted-policy draft list/detail reads, review, approval and publication, Employee published-policy reading and acknowledgement, `POST /api/v1/anomaly-detections/runs`, `GET /api/v1/ai-alerts`, `GET /api/v1/ai-alerts/models`, `GET /api/v1/ai-alerts/:alertId/explanation`, `GET`/`POST /api/v1/ai-alerts/:alertId/feedback`, `POST /api/v1/ai-alerts/:alertId/confirm-incident`, `POST /api/v1/ai-alerts/:alertId/false-positive`, and `POST /api/v1/event-sources`. Policy publication atomically activates the policy, marks the approved version `PUBLISHED`, supersedes its prior current version and sets `current_published_version_id`. Another 98 historical V1 method/URL contracts are registered in `src/routes/legacy-v1-route-contracts.ts`; each currently returns HTTP 501 and is marked pending in OpenAPI. Legacy V3 handlers and tests are preserved in `reference/legacy-v3/`, but are not executed. Do not re-register those handlers against the V2 database; port each use case to the new schema first.

Use route → controller → service → repository → Prisma for each new use case. Update `src/routes/index.ts` and `src/docs/openapi.ts` only when the corresponding endpoint is real and tested.
