# V2 modules

Password login returns HTTP 401 `ACCOUNT_LOCKED` with message `Account is LOCKED` only after a correct password is verified for a LOCKED account. Unknown accounts receive HTTP 401 `ACCOUNT_NOT_FOUND` with message `Account does not exist`. Inactive accounts with a correct password receive HTTP 401 `ACCOUNT_INACTIVE` with message `Account is INACTIVE`. Incorrect passwords retain generic `INVALID_CREDENTIALS`; locked accounts never receive a new session.
Complete Risk Review (`POST /risks/:riskId/review/complete`) is Owner-only with Serializable stale/duplicate/pending guards and current assessment/control checks. Requires new residual after opening and a current standalone inherent basis. Snapshots completion/conclusion/basis/old and next deadlines in RISK_REVIEW_COMPLETED. Uses internal SECURAAI-REVIEW-CYCLE-v1 (Critical 1, High 3, Medium 6, Low 12 calendar months, Vietnam completion day, end-of-month clamp). Earlier dates allowed. Status and acceptance unchanged, no migration. Detail exposes reviewHistory and canCompleteReview. Acceptance submission is blocked while a review is open (409 RISK_REVIEW_IN_PROGRESS); completion unlocks eligibility subject to all existing checks. No email/cron.

Risk Review start supports OPEN/UNDER_TREATMENT/ACCEPTED for the active assigned Owner, rechecking pending acceptance, current review and expected revision under the Risk row lock. RISK_REVIEW_OPENED snapshots opener/name/prior deadline/reason in existing audit_logs. Detail returns nullable currentReview; register adds reviewInProgress via one scoped batch audit read. Missing legacy snapshot fields remain null. Deadline unchanged. Existing approved acceptance ends its prior reopened review for compatibility; standalone Complete Review now records completion and schedules the next deadline. No migration.

`GET /api/v1/assets/owner-options?q=` provides bounded, case-insensitive active-user name/email search for Assign Asset Owner. Active Security Officers only; 10 results, deterministic name/ID ordering, minimal ID/name/email projection. Owner assignment rules remain unchanged (active users), not restricted to Risk Owner's Employee rule. No schema migration.

Risk Detail also returns `assetContextReviewRequired`, based only on successful `ASSET_CONTEXT_UPDATED` audit events for recorded linked assets strictly after the latest identifiable standalone inherent assessment. No assessment or audit evidence yields false. Reassessing inherent risk clears prior context warnings; residual/target updates do not. No automatic rating or permission changes.

Link Asset Context cycle errors include `error.details.path`, an ordered array of code/name labels showing one dependency loop back to the selected asset. Validation remains inside the Serializable transaction; no write or audit is made for rejected cycles.

Risk Detail returns `assetClassificationReviewRequired`: linked asset `classified_at` later than the latest standalone inherent assessment (`inherent_rating` present, `residual_rating` null, excluding target definitions). Residual/target updates do not clear the advisory. Missing timestamps or no identifiable inherent assessment produce false. A newer inherent assessment clears it. This is advisory only; ratings, acceptance rules and stored history are unchanged. No migration.

Asset classification: classification changes now append `ASSET_CLASSIFICATION_UPDATED` in the same transaction as the asset update. Snapshots include four impacts, criticality, data sensitivity, both rationales, methodology versions and assessor/time. First classification uses null before; legacy current values are snapshotted on the next change, with no invented historical events. Identical values/bases/methods do not update or log; reason-only changes do. `GET /api/v1/assets/:assetId/classify-criticality/history` is paginated and scoped to active Security Officers or current Asset Owners, including archived assets. Writes remain active-Security-Officer-only on active assets and never recalculate related Risks. Existing audit_logs only; no schema change.

Asset context history: `PUT /api/v1/assets/:assetId/context` writes `ASSET_CONTEXT_UPDATED` to existing `audit_logs` in the same Serializable transaction as changed links. Snapshots preserve IDs and names/codes of the business service, dependencies and event sources; unchanged selections (including order-only changes) do not write or log. `GET /api/v1/assets/:assetId/context/history?page=1&limit=10` returns bounded newest-first before/after history to active Security Officers or the current Asset Owner, including archived assets. Raw audit metadata is not exposed. No schema changes or historical backfill; existing retained inactive links remain supported.

Owned draft detail is implemented by `GET /api/v1/compliance/policies/:policyId/drafts/:versionId`. Active Security Officers can read only versions they authored on policies they own, with both statuses DRAFT (same scope as drafts/mine). Other records return 404. Existing V2 tables and frontend detail contract are reused. Current pending legacy count is 63; older use-case counts below are historical.

Audit, Security & Reporting supports scoped PDF, Excel and CSV report generation through `POST /api/v1/reports/exports` and bounded export-history reads through `GET /api/v1/reports/exports`.

UC23 Risk acceptance uses current Control/Evidence checks shared with Assess Residual, including all Threat/Vulnerability edits. Submission records a fresh residual and immutable assessment/plan/control basis in existing audit_logs without changing the plan. Approval by the existing active Security Officer/Executive group verifies the submitted basis, excludes the requester, and preserves separate Owner and Approver reasons. Expired/stale Pending requests can be rejected, never approved. Legacy requests lacking a verifiable basis must be rejected/resubmitted; overwritten legacy justification cannot be recovered. Detail returns actor-scoped acceptanceWorkflow/canDecide and expired flags. POST /risks/:riskId/review allows the Owner to reopen an Accepted Risk using reason + expectedUpdatedAt, preserving decisions and requiring new Residual before another acceptance. No schema changes, cron renewal, named-approver assignment or email routing. Dates remain inclusive UTC calendar dates.

Audit, Security & Reporting exposes the scoped Security Officer/Executive security-posture dashboard through `GET /api/v1/dashboard/security-posture`. Integration API keys support bounded search/filtering plus Admin-only scope/expiration updates, rotation and revocation with audited lifecycle changes.

Incident progress: PATCH `/incidents/:incidentId/progress` records the Security Officer's manual readiness assessment for forward, non-closing transitions, with stale-state guards and audited exceptions. GET reads paginated history. Classification, assignment and response journals never change phase; action counts do not prove or gate completion. Leaving Recovery requires the officer's restoration/validation attestation. Exact ordering/restrictions are SecuraAI product decisions, not universal vendor rules. Existing V2 tables/statuses are retained; no schema change or data rewrite. Only the corresponding PATCH legacy contract is removed (71 pending).

UC62: **Incidents → Actions → Root cause & lessons learned** replaces preview findings with the V2 API. GET/PATCH `/api/v1/incidents/:incidentId/analysis` reads/saves the unique `incident_analysis` (root cause, lessons learned, recommended improvements); GET `/analysis/history` paginates before/after audit snapshots. Active Security Officers write only in LESSONS_LEARNED or CLOSED; Security Officers and Executives can read. Required `expectedUpdatedAt` (null initially) prevents stale overwrites. Authenticated analyst and save time are server-owned. Findings/History tabs refresh after save; unsaved input survives tab changes and failed saves. Saving never changes incident status or completes recommendations. No schema changes. 71 legacy routes remain pending after progress migration.

UC61: Record Recovery Actions uses POST/GET `/api/v1/incidents/:incidentId/recovery-actions` and existing V2 `incident_actions` with phase `RECOVERY`. Active Security Officers record completed restoration steps and performed time; the authenticated performer and audit are saved atomically. History is paginated and refreshes after saving. Closed incidents are read-only; recording requires RECOVERY or LESSONS_LEARNED and never changes phase. Verified completion is confirmed separately through PATCH /incidents/:incidentId/progress. No schema changes; 71 legacy contracts remain pending.

UC60 exposes `POST/GET /incidents/:incidentId/eradication-actions` through route → controller → service → repository. Existing `incident_actions` records phase `ERADICATION`, description, authenticated performer and performed time; an atomic audit accompanies writes. History is paginated and phase-scoped. No schema changes or legacy routes are required (71 pending).

UC59: `POST/GET /api/v1/incidents/:incidentId/containment-actions` records and lists completed containment actions using existing `incident_actions`. Only active Security Officers may write; Security Officers and Executives may read paginated history. Writes append an audit atomically and preserve the incident phase; recording requires CONTAINMENT or a later non-closed phase. Closed incidents are read-only. These action URLs do not replace pending contracts. 71 legacy contracts remain pending after progress migration.

UC57: `PATCH /api/v1/incidents/:incidentId/severity` lets active Security Officers classify severity (`low`, `medium`, `high`, `critical`) with a 10–2000 character rationale. Severity and its `INCIDENT_SEVERITY_CLASSIFIED` audit record are saved atomically. Optional `expectedUpdatedAt` guards stale edits; closed incidents return 409. List/detail responses include classification count and the latest rationale, officer and time. There are 71 pending V1 contracts.

Notification & System Logs implements Admin-only in-system and email sending through `POST /api/v1/notifications` and `POST /api/v1/notifications/email`. All active roles can read and update their own supported delivery channels through `GET/PATCH /api/v1/notifications/preferences`; preferences default to both channels enabled and updates are audited. Inbox listing, read state and notification history remain separate use cases.

User Activity Audit Log is implemented through Admin-only `GET /api/v1/audit/user-activities`. It returns bounded, newest-first user-actor records with actor, action, affected resource, timestamp and outcome, plus non-sensitive source metadata. Search, outcome/resource filters and server-side pagination are supported; raw before/after payloads are intentionally excluded.

Admin-only `POST /api/v1/notifications/email` sends text-only email through the configured SMTP transport to up to 20 explicitly selected active users. It snapshots recipient email addresses, records `PENDING` delivery rows before network I/O, then marks each attempt `SENT` or `FAILED` without exposing provider errors. Partial delivery is returned with sent/failed counts. Retry, templates, attachments, HTML email and bulk role audiences are outside this use case.

Control Evidence supports HTTPS references and private local/demo file uploads. `GET`/`POST /compliance/controls/:controlId/evidence`, `POST /compliance/controls/:controlId/evidence-links`, `POST /compliance/controls/:controlId/evidence-files` and `GET /compliance/evidence/:evidenceId/download` use `evidence_items` and `control_evidence_links`. Upload accepts one PDF, PNG, JPG/JPEG, TXT, CSV or XLSX up to 10 MB, validates extension/MIME/content, stores it under an opaque key in `uploads/control-evidence`, records SHA-256 and serves it only through ownership-scoped download with an audit event. Files are not malware-scanned, so this storage is explicitly local/demo rather than production-grade. Security Officers and assigned Employee Control Owners can act. Upload/reference creation and linking do not mark Evidence reviewed, create an effectiveness result, rewrite assessment history or recalculate Risk. Existing Evidence remains reusable and validity is checked for new assessments. The schema links Evidence to the Control rather than to an immutable assessment snapshot; review, edit, unlink, archive, malware scanning and versioned custody remain separate use cases.

Control catalog preparation for Risk Assessment is implemented through `POST /compliance/controls`, `GET`/`PATCH /compliance/controls/:controlId` and `GET /compliance/controls/owner-options` under the API prefix. These extend the existing shared `security_controls` resource and `/compliance` route contract; the physical compatibility module is not a claim that Assess Control Effectiveness belongs to Policy Management. Catalog Create/Edit is Security Officer-only. Contextual Employee Control Owners gain `compliance.assess-controls` navigation only while assigned at least one control; assessment APIs retain resource ownership checks. Codes are immutable, new owners are active Employees or Security Officers, and edits require a reason and exact revision. Applicability/implementation are locked after the first assessment to prevent historical effectiveness from being silently reinterpreted. Evidence, assessments and Asset/Risk/Incident links are not changed by catalog writes. No new database tables or migrations are needed. Evidence upload and explicit Control-to-Risk link management remain separate use cases.

Business Service Deactivate: Security Officer `GET /api/v1/business-services/:serviceId/deactivation-check` shows usage; `POST /:serviceId/deactivate` requires expectedUpdatedAt, confirmationName and reason. Only unused Active services may transition to Inactive: Active assets and directly scoped Open/Under treatment/Accepted Risks block; Archived assets and Closed/Archived Risks remain linked for history. Actor/status/version/usage checks plus audit are atomic in a Serializable transaction; concurrent changes return 409. No deletion, reactivation, relinking, Risk synchronization or schema changes. The reason, actor and timestamp live in existing audit_logs (BUSINESS_SERVICE_DEACTIVATED), not new Business Service columns.

Business Service Edit: `PATCH /api/v1/business-services/:serviceId` permits active Security Officers to edit name, description and owner only on Active services. Requires expectedUpdatedAt; rejects stale writes, duplicate names and new inactive owners. Retains unchanged inactive owners, supports explicit unassignment, and records before/after metadata atomically in audit. Status, identity, Asset membership and Risk scope are not editable here.

Business Service creation: `POST /api/v1/business-services` and `GET /api/v1/business-services/owner-options` require an active Security Officer. Creates Active service only, optional active owner, normalized nonduplicate name; atomic audit, no asset links or Risk synchronization, no schema changes. See OpenAPI for validation limits. Name concurrency guard covers this API path, not direct database inserts.

IT Asset Management also exposes read-only `GET /api/v1/business-services`, `GET /api/v1/business-services/:serviceId`, and `GET /api/v1/business-services/:serviceId/assets` for active Security Officers. List/search and linked assets are bounded and paginated; inactive services and archived assets remain visible for review. These read endpoints do not modify any record, relink assets or synchronize existing Risk scopes. See the corresponding OpenAPI contracts.
